# Agents

1. Follow general code quality guidelines at https://gitlab.com/rpnx/rpnx-coding-standards when writing code.
2. Quxlang QXC is a fully deterministic, hermetic, and reproducible cross compiler, don't introduce any code that changes those properties.
3. Put temporary test files in a directory named `tmp` in the root of the repository, unless you've been asked to put them elsewhere. This directory is already in `.gitignore`.
4. Please ensure that your code adheres to the Zero Overhead Principle. We generally prefer undefined behavior over runtime checks that introduce significant overhead.
5. Quxlang is usually built by running `csetup download` to get dependencies, then `cbuild -c Release` from the `misc/build` directory. If the tool is not installed, you can get it at https://gitlab.com/rpnx/cbuild-go, usual commands to download it is something like `go install gitlab.com/rpnx/cbuild-go/cmd/cbuild@preview && go install gitlab.com/rpnx/cbuild-go/cmd/csetup@preview`. If that doesn't work, try "latest" instead of "preview". CMake, Ninja, Git, and a C++ compiler are also required.
6. LLVM will take a long time to build, try not to use `cbuild clean` as that will delete the LLVM build directory. Instead when needed clear only Quxlang's build directories using `cbuild clean -t quxlang`.
7. `cbuild test` will run tests, but it will do so in many different build configurations, you might want to use `cbuild test -c Release` to just run Release configuration tests. It will auto-rebuild any changed targets.
8. Prefer not to add new GTEST cases in .cpp files if the same thing can be tested from a Quxlang STATIC_TEST, UNIT_TEST, or DUAL_TEST. Prefer DUAL_TEST unless you have a reason to use another kind of test.
9. It's recommended to do end-to-end validation by running qxc against the testbundle and then running the resulting test executable for the current OS/platform combination.
10. Compiling on Ubuntu probably wont work. Use a container like podman with an arch based image and you're more likely to get a working build. This will be fixed eventually.
11. The compiler is not allowed to generate any calls to lower-case named identifiers or arguments, except when provided those identifiers by user code.
12. If you are reading this repo not working on it, `.qxs` files in the testbundle subfolder are good examples of currently supported Quxlang code. Quxlang.dev also has examples with documentation although it's not always up to date. The information on the website is stored in `website/`.
13. Use a formal, technical, and declarative documentation style. Write complete grammatical sentences with explicit subjects, predicates, and conditions. Name the relevant language construct directly instead of addressing the reader. Avoid imperatives, second-person language, casual phrasing, sentence fragments, implied clauses, ambiguous pronouns, invented terminology, and unnecessary contrastive framing. Use conventional technical vocabulary consistently.
Overview pages are example-oriented. They introduce each feature through representative code, explain its purpose and typical applications, establish the relevant intuition, and summarize important performance or implementation tradeoffs. Overview pages omit exhaustive rules and minor edge cases.
Reference pages specify the complete technical contract. They document syntax, accepted forms, semantic constraints, type behavior, overload resolution, lifetime effects, failure conditions, target restrictions, implementation status, and relevant edge cases. Their structure and level of detail should resemble cppreference.
Both sections use the same formal technical voice. The sections differ by coverage and level of detail, rather than by tone.
14. The use of double-underscore in symbols, like `__BODY` is restricted to implementation detail identifiers that cannot be declared normally in user code. For example, an unnamed variable might be given the name `__VAR0` or `__VAR1`, or `__VTABLE` or `__BASE` might be used to implement inheritance.
